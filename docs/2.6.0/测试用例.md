## 执行顺序

开发时按改动复测。删更新器后构建一次并打开设置（C01、C02）；精简「关于」走 C03；去掉通知和图标选项后，复用同一对应用依次验证规则编辑、短按 Fn 和权限（C04、C05、C07–C09、C12）。安装位置用 Release 副本验证（C06）。同一候选构建、同一环境下的结果可供多个用例引用。

集成后在 macOS 14 真机先跑 C07、C10：在 A 中单按 F1，切入 Chrome 选词按 F4 并试亮度键，再切回 A 单按 F1。接着暂停、恢复并正常退出（C14），核对搜索映射和键盘状态。其余升级和恢复场景按 C01–C18 在候选包验收时统一记录。现有手工步骤和只读产物检查即可执行。

使用带内置键盘的 Apple Silicon Mac、Google Chrome 和两个可切换的应用 A、B。记录 macOS 版本、Chrome 版本、应用构建号、初始键盘模式及已有键盘映射。C02、C12 的授权场景使用独立测试账户，C13 使用有 2.5.2 配置的账户。执行后按编号记录通过、失败或未测，并附实际现象。

## 构建和产物检查（C01）

在仓库根目录执行。选择安装了本项目所需 SDK 和签名身份的 Xcode，使用当前锁定的 Swift 包。下例把 DerivedData 放入本次测试的临时目录。若另行生成发布 ZIP，还应对 ZIP 中的 .app 重做同样检查。

```sh
fluor_build_dir="$(mktemp -d)"
xcodebuild -project Fluor.xcodeproj -scheme Fluor -configuration Debug -derivedDataPath "$fluor_build_dir" build
xcodebuild -project Fluor.xcodeproj -scheme Fluor -configuration Release -derivedDataPath "$fluor_build_dir" build
fluor_app="$fluor_build_dir/Build/Products/Release/Fluor.app"
plutil -p "$fluor_app/Contents/Info.plist"
fluor_executable=$(/usr/libexec/PlistBuddy -c 'Print CFBundleExecutable' "$fluor_app/Contents/Info.plist")
for fluor_config in Debug Release
do
  fluor_bundle="$fluor_build_dir/Build/Products/$fluor_config/Fluor.app"
  /usr/libexec/PlistBuddy -c 'Print LSMinimumSystemVersion' "$fluor_bundle/Contents/Info.plist"
  xcrun vtool -arch arm64 -show-build "$fluor_bundle/Contents/MacOS/$fluor_executable"
done
otool -L "$fluor_app/Contents/MacOS/$fluor_executable"
rg --files --hidden --no-ignore "$fluor_app/Contents" | rg 'Sparkle|dsa_pub\.pem|ReleaseNotes\.rtf'
```

两次构建分别记录退出状态；任一失败先记录首个错误。核对 Info.plist 的 CFBundleShortVersionString、CFBundleVersion、CFBundleIdentifier，以及已退役的更新键。最后的筛查预期零匹配，rg 此时返回 1。将产物检查与 C02 的重复启动合用，可区分「本次恰好没有新版本」和「候选包已移除更新器」。

## 如何复测两项核心行为

**逐应用规则（C07–C09）。** 建议用终端作为 A、文本编辑作为 B。在 A 打开终端键盘查看方式，例如运行 `cat -v`，按 F1 再按回车，观察功能键转义序列，结束时按 Ctrl+C。B 使用同一物理按键看亮度是否调节，先把亮度设在中间。若测试 Mac 有自定义系统快捷键，先在 2.5.2 用同一按键取得对照。每次都先把对应窗口置前，再记录按键结果。菜单和规则表的勾选状态只作为佐证。

**Chrome 搜索（C10–C12）。** 在相同 Chrome 窗口内使用普通网页，准备含「C++ 测试」的可选正文和足够的空白文本。用无真实凭据的密码框验证安全输入。按键前记录标签数，按一次物理 F4，核对新增标签数、主机 www.google.com 及解码后的 q。正例应新增一个标签，q 为完整原文。负例应新增零个。若结果页因网络原因未加载，分别记录已打开的目标地址和网络结果。检查亮度及音量时始终让 Chrome 在前台。

**Chrome 优先级（C10）。** 在规则编辑器中显式把 Chrome 设成标准功能键，A 也设为标准功能键。在 A 验证 F1，再依次切入 Chrome、选词、按 F4、按亮度键、切回 A、按 F1。期望依次看到标准功能键输入、一张新结果页、亮度变化、再次出现标准功能键输入。重新打开规则表时，保存的 Chrome 规则仍为标准功能键，验证临时生效模式与持久化规则相互独立。

**辅助功能（C12）。** 从没有给此测试副本授权的账户启动，用系统设置确认授权状态。暂缓授权后先验证 A、B 自动切换，再试 Chrome F4；记录实际系统默认 F4 行为以及搜索标签数。授予辅助功能后按 README 切走再切回 Chrome，搜索应成功。整个测试无需更改系统通知授权。此步骤涉及实际键盘和 Chrome，执行时使用经授权的真机测试环境。

## 状态恢复的判定标准（C13–C17）

测试前记录启动时键盘模式。正常退出的每一行都应从 Chrome 前台、搜索已成功的候选包开始，通过菜单正常退出。每行结束后重新设定下一行的启动基线。

| 退出设置 | 准备 | 正常退出后的结果 |
| --- | --- | --- |
| 关闭「退出时重置」 | 启动前设置为标准功能键，在 Chrome 中使媒体键模式生效 | 保持最近生效的媒体键模式，Fluor4me 的 F4 搜索映射已移除 |
| 重置并恢复启动模式 | 启动前设置为标准功能键，在 Chrome 中使用搜索 | 恢复标准功能键，搜索映射已移除 |
| 重置并指定模式 | 启动前设置为媒体键，退出目标设标准功能键 | 采用指定的标准功能键，搜索映射已移除 |

- **升级记录。** 在专用账户把 2.5.2 的应用 A、B 名称、路径、规则、默认模式、触发方式、退出行为和构建号填入记录。用相同安装路径、同一偏好域升级。先比对规则列表再实按验证，避免启动新副本时旧版本仍在响应。若需复查 2.5.1 旧标识迁移，使用保有旧域的测试账户，验证已有新域值优先；新域缺少整个 AppRules 键时，旧域的规则集合才会复制进来。
- **映射记录。** 可在终端用只读命令 `hidutil property --get UserKeyMapping` 记录基线。多键盘环境要核对内置键盘服务。可预先安排延时采样再切入 Chrome，以免切去终端时已触发映射清理。对照物理键的实际表现和映射内容。F4 来源为 0xC00000221，本应用的目标为 0x70000006D。
- **强退复现。** 使用专门的测试实例并核对进程号。从另一终端安排延时强退，再将 Chrome 置前并确认可搜索；在定时动作发生前保持焦点。测试人员切到活动监视器再手动强退，会先触发正常的离开 Chrome 清理，无法验证异常恢复。重新启动时记录清理前后映射，测试完正常退出候选包。
- **登录、睡眠与显隐。** 记录登录启动原值和 macOS 版本。系统菜单栏开关的恢复步骤在 macOS 27 验证，其他版本按其支持的路径记录。分别验证后台功能和图标可见性，避免把图标隐藏误判为应用退出。
